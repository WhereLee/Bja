# 道闸（升降杆）biz 模块 · 设计说明

> 定位：在 inteink 权限脚手架之上，重建“升降杆自动策略管理”业务域；本文把**对象模型 → 可靠性 → 调度正确性 → 测试 → 压测**串成一条线，并记录关键取舍（含“刻意不做什么”及理由）。

## 1. 业务是什么
配置“**何时升/降哪些杆**”：建杆 → 绑转换器（设备接入台账）→ 配策略（时间窗）→ 审核通过 → 自动生成成对 Quartz 定时任务（begin 做动作、end 反向）→ 到点或手动驱动闸机 → 动作与审核全程留痕。支持暂停/恢复/删除、手动立即执行、实时看板。

## 2. 对象模型（源于真实数据表，不臆造）
| 对象 | 表 | 职责 | 关键状态 |
|---|---|---|---|
| 升降杆 Rod | biz_lifting_rod | 被操作、有状态的业务对象 | rod_state(0默认/1升/2降)、rod_offline(0离线/1在线) |
| 转换器 Converter | biz_converter | **可寻址设备**：sn/ip/port + rod_id 绑定 | 逻辑删除 status |
| 策略 Strategy | biz_lifting_strategy | “何时升/降哪些杆”+审核关口 | action、type、check_state |
| 时间窗 Detail | biz_lifting_strategy_detail | 一次抬落 begin/end | — |
| 策略↔杆 | biz_lifting_strategy_rod | 多对多绑定 | — |
| 审核日志 | biz_lifting_strategy_log | 策略生命周期审计 | log_type |
| 动作日志 | biz_lifting_rod_log | 每次升/降留痕 | type(手动/自动)、action、result |
（复用：sys 用户/角色/菜单/权限、job 模块 ScheduleJob。）
**关键判定**：可下发“设备”= **转换器**（有地址、可命令、能回报）；杆是被驱动/回报的业务对象；电机不建模。数据模型无“路口/两杆互锁/防砸地感”，故不臆造这些。

## 3. 设备下发的分层与可靠性
```
LiftingRodServiceImpl.operateRod
  → ReliableRodCommandService（编排：并发/去重守卫 + 有限重试退避 + cmdId）
    → RodCommandGateway（传输：单次下发，返回 DeviceResult）
       MockRodCommandGateway（默认恒成功）| HttpRodCommandGateway（按 converter.ip:port 寻址真实/虚拟设备）
  → @BizLog 统一记 rod_log（成功/失败）；失败：网络类置 rod_offline=0（转人工可见）
```
- **DeviceResult**：SUCCESS / TIMEOUT / OFFLINE / DEVICE_REJECT / SKIPPED_DUPLICATE，带 `isRetryable()`（仅网络类可重试）。
- **重试**：只对可重试类，上限 3、指数退避；拒绝/成功不重试。
- **幂等**：同杆“进行中”守卫 + 成功后短窗去重（进程内，单机）。
- **人工兜底 + 对账**：失败不空转、标离线；`reconcile(rodId)` 手动 + `ReconcileJob` 定期，**以设备回报真实态校正** `rod_state/rod_offline`。

## 4. 调度与时间正确性
- **时区固定**：策略 trigger 显式用 Asia/Shanghai，不随 JVM 漂移。
- **misfire = DoNothing**：错过不自动补跑（物理动作补做有风险），错过留痕。
- **END 前置状态守卫**：反向动作只在杆处于 begin 期望态时执行 → 根治“审核晚于 begin/漏触发 → 只降不升”的半程。工厂 `warnIfHalfWindow` 留痕。
- **月末/无效日**：cron 生成对 29/30/31 告警提示。

## 5. 横切（AOP）
- `@BizLog` + 切面 + Handler：领域事件日志（rod_log / strategy_log），取代内联写；`@Order(0)` 在事务外。
- `@TimeCost`：方法耗时，超阈值 warn；`@Order(1)`。
- 与平台级 `@SysLog`（接口审计 sys_log）分工清晰，不双写。

## 6. 实时看板
`GET /biz/rod/liveStatus`：读**设备态快照缓存**（`DeviceStateCache` 每 5s 并发刷新一轮）→ 汇总在线/离线/未绑定 + 每杆实时态；前端 `dashboard.html` 5s 轮询展示。**读时不再现场探测设备**（见压测）。

## 7. 测试
- 单元（15+，不连库/网络）：cron 生成、结果分类、重试/去重、END 守卫、看板聚合。
- 集成/E2E：真实 MySQL 下走完整链路（见 test 目录）。
- CI：`mvn clean package` 会跑测试；历史草稿测试用 surefire `excludes` 排除（不删）。

## 8. 性能压测（P1：app+MySQL+设备农场同机）
`liveStatus` 基线串行探测 500 设备 → 高并发吞吐坍塌；经**有界并发探测 + 设备态快照缓存**：并发30 **QPS 1.5→126、P99 6.9s→0.8s、错误 30→0**。详见 `docs/性能压测.md`。

## 9. 刻意不做（及理由）
- **MQTT / 云端设备农场 / WebSocket**：本项目简单、虚拟设备只是物理设备“替身”，现有 HTTP（多实例/按地址/可失败/回报）已足够；无设备主动上报事件源时 WS=轮询换皮。**仅在接真实硬件协议/需主动上报时**再作为 `RodCommandGateway` 的一个实现引入。
- **Redis / 多实例**：鉴权走 token→DB、缓存/幂等目前进程内、单机足够；**当决定横向扩容（多实例）时**再引入 Redisson 做分布式锁 + 共享缓存 + 集群调度（否则“凑名词”）。
- **监控指标栈 / 限流**：非当前规模所需。

> 原则：**没有真实问题就不上技术**；深度靠“分层、可靠性、测试、调度正确性、可量化的优化”这类想得清楚的点，而非堆名词。
